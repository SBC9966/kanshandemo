# 知山行 · 产品说明计划书

> 副题：**看山不是山，让知识有路径**
> 一句话：把知乎上的真实讨论，组织成一条**走得完**的知识路径。
> 参赛活动：知乎黑客松 2026 校园新锐季（`zhihu_hackathon_2026_p2`）

---

## 一、创作思路：从"刷到"到"走完"

**我们想解决的问题。** 今天了解一个话题，大多数人得到的是两种东西：一种是刷到的一条条讨论——有信息、有情绪、有立场，但彼此孤立；另一种是"三分钟看完""十条金句"式的摘要——好读，但经不起追问。两者的共同点是：**用户从没走完过任何一条路**，因此很难说清"我到底理解了没有"。

**我们的判断。** 知乎真正稀缺的不只是"某一条高赞回答"，而是**一群人围绕同一个问题形成判断的过程**：有人给证据、有人反驳、有人补充边界。这个过程本身值得被完整地走一遍，而不是被切成一句结论。

**我们的答案：把讨论变成路径。** 每座"知识山"分五层营地，由浅入深：

| 层 | 用户在做什么 |
|---|---|
| 山脚 · 认识 | 先看清问题到底在问什么，别急着要答案 |
| 山麓 · 背景 | 把它放回历史与语境里 |
| 山腰 · 核心 | 认识不同的思想/技术路径 |
| 高处 · 分歧 | 这里**没有统一答案**——学怎么对读，而不是站队 |
| 山顶 · 延伸 | 回到自己的生活与判断 |

每一层都必须**先摆材料与出处，再动手做一次实验，最后用一次理解确认把话说清楚**。实验与确认都完成，这一站才算走过；走完五层，山顶把你的判断连成一张脉络图。

![图 1　首页：六座知识山，每座五层营地；前三层在路演模式下默认开放，评委可直达](docs/shots/01-home.png)

**为什么是"山"。** 因为爬山这个隐喻天然包含了三件我们希望用户经历的事：起步时视野有限、越往上越陡、只有到了山顶才能看见全貌——而"看得更清楚"正是这套产品的终点，不是"读完"。

## 二、用户怎么走完：可实际操作的五段

1. **先看材料**（每层第一屏）：本地策展出处 + 知乎真实回答片段，每一条都能点进原文；明确标注"这次实际读取到哪里"（`已读相关段落` / `仅检索摘要`）。
2. **亲手探索**：分类、排序、配对、视角选择、反思五类互动实验；操作会真实改变实验状态，不是点一下播动画。
3. **理解确认**：三道选项里选一个更贴近内容的说法，选完给解释；**实验 + 确认都完成**这一站才算走过，并在原地弹出「进入下一站」——不用自己回地图找。
4. **随身向导「阿山」**：一只常驻侧边的小狗向导，随页面给出解释与相关材料；**先把本地知识库检索的答案连同出处摆出来**，命中不足会直接说"没有足够匹配，我不编"；紧接着再补一条**知乎直答**大模型的回答（模型可选，标明是模型生成、附不确定性说明）。
5. **山顶一览**：五层脉络图（峰顶是"这座山在问什么"，脊线串起五站的概念与判断）、六座山的进度一览、跨山路径；可一键导出「考察手记」（含出处与检索记录）。

**路演模式**：前三层营地默认开放，便于评委直接跳进去看内容；后面的营地按真实完成度依次解锁。

## 三、技术方案

**前端（零依赖、可离线）**
原生 ES Module 编写，构建产物是**单文件自包含**的 `index.html`（约 2.6MB，插画/脚本/样式/资料元数据全部内嵌，**零外部请求**），双击即可打开；无框架、无 CDN、无外链字体。服务端也不依赖任何第三方包，只需 Node 20+。

**本地知识层**
49 条策展来源，其中 **33 条知乎问题与专栏入口、16 份公开参考页**；每条都带**读取范围**（`已读相关段落` / `仅检索摘要`）、知识用途与出处。另有本地检索引擎（分词 + 打分）驱动资料馆检索与向导作答。

**3D 微缩沙盘**
内置 three.js 实现的程序化山体：一座主峰 + 五座副峰 + 盘山小径 + 五站装置，60fps 自动运镜与自由观察，用户一拖动即接管。

![图 4　3D 微缩沙盘：程序化山体、盘山小径与五站装置，自动循环运镜，拖动即接管](docs/shots/03-3d-diorama.png)

**时间轴是纯函数**（`update(day)`，无 `Math.random`、无 `Date.now`），因此同一时刻画面永远一致，可重放、可截图、可录屏。

**知乎开放能力接入的工程化**
- 所有调用经**服务端代理**，Access Secret 只留在服务端，前端仅拿到脱敏后的字段。
- **磁盘缓存 + 请求去重 + 分钟级限流**：页面刷新不重复消耗日额度；缓存按"同一问题的不同条数"共享，避免同样内容重复取。
- **失败一律退回最近快照，并如实写明失败原因与快照时间**（额度耗尽 / 未配置凭据 / 网络失败都走这条）；绝不返回编造的成功结果。
- **静态托管也能看到知乎内容**：构建时把已取回的内容固化成前端离线快照，页面上明确标注「离线快照 · 取回于 …（实时内容需服务端在线）」。

**两种交付形态**

| 形态 | 知乎能力 | 说明 |
|---|---|---|
| 静态托管（已上线，GitHub Pages） | 离线快照（标注取回时间） | 保证任何人随时打得开，零依赖 |
| Vercel（配置已就绪） | **实时**（配置 `ZHIHU_API_KEY` 即可） | 仓库内含 serverless 函数与 `vercel.json`，导入仓库即可部署，Hobby 免费额度足够 |

### 知乎 OAuth 登录（代码与测试已完成，等赛事凭证联调）

除了开放平台的接口凭证，我们还按《黑客松 OAuth 接入》实现了**授权码流程**的完整服务端：浏览器访问 `/api/zhihu/oauth/start` → 跳到知乎授权页 → 回调 `/api/zhihu/oauth/callback` → 服务端用 `authorization_code` 换取用户令牌 → 读取 `https://openapi.zhihu.com/user` 的公开资料 → 建立会话。

**安全上守住四条**：① `app_key` 与用户 OAuth 令牌只存在于服务端内存，浏览器拿到的只有一个 `HttpOnly` 会话 Cookie，前端只能读到昵称、头像、一句话介绍；② `email`、`phone_no` 这类敏感字段即使返回也在服务端丢弃，不出网关；③ `state` 用密码学安全随机数生成，绑定当前浏览器会话、10 分钟过期、**回调时先原子消费再判断**，缺失/不匹配/过期/重复使用四种情况一律拒绝，不进入换 token 的步骤；④ 会话有效期以令牌 `expires_in` 为准并封顶 7 天，令牌失效即停止读取，**不会回落到 Access Secret 所属账号**。

**当前状态（如实说明）**：App ID 与 App Key 需要从黑客松赛事页面创建项目后领取，`redirect_uri` 也必须在赛事页面登记（公网 HTTPS）。凭证未到位之前：入口按钮**不显示**（不出现点不动的假登录），点击授权返回的是"服务端还没有配置 OAuth 凭证"。代码、配置模板与 **11 项 Mock 测试**已就绪（覆盖授权 URL 构造、state 四种拒绝路径、换 token 的表单参数与失败处理、用户字段白名单、会话过期），凭证填进 `.env` 即可联调。

**凭证到位后准备做什么**：用授权的收藏与关注生成"属于你的知识山"（需 Access Secret + `X-OAuth-Token` 双凭证）；以及把山顶的「考察手记」发回知乎，形成"读知乎 → 想清楚 → 写回知乎"的闭环。这两项都还没做，写在这里是因为它们才是 OAuth 在这个产品里真正的用途。

**向导「阿山」怎么用直答**：每次提问，阿山先把**本地检索的答案连同出处**摆出来（这段不经过模型，逐条可核对）；紧接着再补一条**知乎直答**的回答。送给模型的不是光秃秃的问题，而是「问题 + 当前营地的导读与要点 + 本地策展问答 + 可引用来源标题」，让它在**本站材料上**作答，而不是凭空生成。界面把两者分得很开：本地那条是策展材料，直答那条带「知乎直答」徽标，并固定附一句"内容由直答模型生成，可能存在错误，判断仍以页面上的来源为准"。

**额度有限，所以做了三件事**：① 同一问题 + 同一模型的结果落盘缓存 30 天，重复提问不再消耗额度（实测第二次提问 0.4 秒返回、未发起请求）；② 每个 IP 每分钟限 3 次；③ 取不到时**退回缓存并写明原因**（含取回时间），没有缓存就如实说取不到，不假装成功。三个模型在面板上可选并标注各自耗时——快答约 3 秒、深度思考会先想一遍、智能体先去知乎翻材料（实测约 47 秒，演示默认用快答）。

![图 5　向导「阿山」：每次提问先给本地检索的答案与出处，再补一条知乎直答的回答（模型可选，问题+模型级缓存）](docs/shots/05-guide-zhida.png)

**合规约定**：只展示服务端返回的摘要片段并给原文链接，不复制全文；不展示/不推测赞同数与浏览数；不把知乎内容改写成本项目创作；不批量高频调用；模型生成的内容一律标注来源与不确定性。

## 五、适配知乎社区的场景价值（重点）

**1. 给优质讨论一个"第二入口"：从话题旁边，变成学习路径上必经的一站。**
今天的知乎讨论大多在被需要的那一刻被检索到，然后被划走。我们把同一批讨论放进一条路径里：用户在"分歧层"读到的不是随机一条回答，而是**被标好用途与读取范围**的材料——"这一条用来发现争议""这一条用来核对概念"。同一份内容，从"可能有用"变成"在这一步必须用"。

**2. 把"分歧"变成产品的一等公民，而不是需要被抹平的杂音。**
多数知识产品会替用户收敛结论。我们的第四层恰恰相反：明确告诉用户"这里没有统一答案"，并给出一套对读方法（先分事实与观点、再看证据能支持到什么程度、最后判断这条材料适合用来做什么）。**这直接对应知乎最真实的形态**——一个问题下面本来就并存多种立场，产品不该假装它们不存在。

**3. 让创作者的努力被"走完"，而不是被"刷过"。**
一条认真写的回答，在信息流里的生命周期可能只有几秒钟。放进路径中，它会被：放在具体的层与位置上、标注本次读取范围、被一次互动实验与一次理解确认反复使用。用户走完后导出的「考察手记」**带完整出处**，可以把"我读到了什么、我判断到什么"带回社区继续讨论——这是对流量的另一种回报方式。

**4. 对生态有分寸：额度感知与诚实降级是产品的一部分。**
知乎开放能力的额度是稀缺资源。我们把"每次调用花在哪"做成了产品逻辑：能缓存就缓存、能合并就合并、取不到就说取不到（并显示最近快照的时间）。页面上没有任何"伪造的赞同数与检索命中数"。一个健康的社区应用，应该示范**怎么有节制地使用社区数据**。

**5. 一套可复制的模板：任何垂直话题都能长成一座山。**
"五层营地 + 出处标注 + 互动实验 + 理解确认 + 山顶脉络"这套结构已经跑通六座山：认知偏差、伦理入门、迷因群岛、AI Agent、独立思考、存在主义。换成任何垂直话题（医学常识、法律入门、职场方法论……），只需要换内容与实验设计，产品骨架不变——**这让知乎的垂直内容有了一条稳定的产品化路径**。

**与知乎现有功能的关系：不做"又一个搜索"，做它们下游的组织层。**
搜索解决"找到"，热榜解决"当下在讨论什么"，直答解决"快速得到一个综合答案"。而知山行解决的是最后一公里：**把已经找到的东西，变成一条用户真的走得完、并能讲清楚自己收获的路。** 三者可以并行使用，我们负责把结果组织起来。

## 七、边界与下一步（不写成"已完成"的部分）

- 向导的检索是**关键词打分**，不是语义模型；命中不足时它会明确说"没有足够匹配"，并给出去资料馆检索的出口。向导里的大模型回答来自**知乎直答**，是"另一种说法"而非本站结论，额度紧张时只缓存不重问，取不到就不显示。
- 3D 沙盘是**示意性微缩舞台**，不是测绘地形；六座山共用同一套山形骨架，差异在配色、天气、植被与文案。
- 静态托管版看到的是**离线快照**（页面标注取回时间）；实时内容需要服务端凭据在线（Vercel 配置已就绪）。
- **OAuth 登录尚待联调**：授权流程、安全校验与 Mock 测试都已完成，但 App ID / App Key 与回调地址需要赛事页面发放与登记；在拿到凭证之前，界面不显示登录入口，也不会用 Access Secret 冒充用户身份。
- 下一步计划：分歧层做成"可对读双栏"；为资料馆来源补懒加载与分页；把五层模板扩到更多垂直话题，并开放"自定义主题"生成路径（服务端已具备 `/api/generate` 通道，配置模型即可开启）。
